IssuerProvisioningKit – Architecture

IssuerProvisioningKit answers one question for an issuer's Wallet extension: which of the issuer's cards can still be added to this iPhone, and to the paired Apple Watch.

This document follows the 4+1 view model: the logical, process, development and physical views, tied together by scenarios.

2. Process View

One call from Wallet runs entirely on the caller's thread and finishes before status returns.

1Wallet → extensionstatus(completion:)
↓
2extension → Providerstatus(completion:)
↓
3Provider → Evaluatorevaluate(lastDigits:requiresAuthentication:)
↓
4EvaluatorDrop empty and duplicate lastDigits. Return early if none are left.
↓
5Evaluator → Repository → PassKitPKPassLibrary.passes(of: .secureElement), converted to SecureElementPassRecord
↓
6EvaluatorIndex active passes by suffix. Deactivated passes are dropped.
↓
7. For each lastDigits entry, until both answers are true
7aEvaluatorSuffix not found: passEntriesAvailable = true
or
7bEvaluator → Repository → PassKitSuffix found: canAddSecureElementPass(primaryAccountIdentifier:), skipped once the Watch answer is true
↓
8Evaluator → ProviderProvisioningAvailability, mapped by PassKitStatusMapper
↓
9Provider → Walletcompletion(PKIssuerProvisioningExtensionStatus), before status returns

Timing

Wallet ignores an answer that takes more than 100 ms.

  • Synchronous. completion is called before status returns. There is no thread hop and no queue to wait for.
  • Wallet is read once per call and indexed by suffix: O(n + m) time for n passes and m lastDigits, instead of O(n × m).
  • PassKit calls are the real cost. Each one is an XPC round trip to the system Wallet service, far slower than the Swift around it. The evaluator therefore:
    • skips empty and duplicate lastDigits,
    • stops asking about the Watch once one card is addable there,
    • stops looping once both answers are true,
    • does not read Wallet at all when lastDigits is empty.

Concurrency

IssuerProvisioningStatusProvider only holds constants, so concurrent calls do not share mutable state. A test calls status from 100 threads at once.

State

Nothing is cached between calls. Each call reads Wallet again, so a card the user just added is taken into account.

The test folders mirror the source folders, so the test for a type is always in the same place.

Dependency injection

Constructor injection only, no container. IssuerProvisioningStatusProvider builds the real graph in its public initializer. An internal initializer takes any ProvisioningStatusEvaluating, which is how tests replace it.

Test doubles are hand-written: spies record calls, stubs return fixed data. PassLibrarySpy and SecureElementPassStub stand in for PKPassLibrary and PKSecureElementPass, which cannot be created with a chosen state in tests.

Line coverage of the framework is 99.2%. The only line not covered is the \.secureElementPass key path in PassLibrary.swift, which runs only when the real Wallet holds a card, so only on a device.

Build

The shared scheme IssuerProvisioningKit runs the tests with coverage limited to the framework target. scripts/build-xcframework.sh produces the binary for distribution; build products are never committed.

Apple Watch
  • Binary. One XCFramework with a device slice and a Simulator slice. Built with library evolution, so it ships a .swiftinterface and keeps working with newer Swift compilers. dSYMs are bundled for crash symbolication.
  • Host. The framework is embedded in the issuer app and runs inside its non-UI Wallet extension on the iPhone.
  • Apple Watch. No code runs on the Watch. Its passes are reached through PassKit on the paired iPhone, so no watchOS slice is needed.
  • Access. PKPassLibrary only returns passes issued for the app. This requires the com.apple.developer.payment-pass-provisioning entitlement and the app and extension IDs in each pass's associatedApplicationIdentifiers.
